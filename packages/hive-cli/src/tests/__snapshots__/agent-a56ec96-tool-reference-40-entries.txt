  ## `tool_reference` content blocks -- full explanation

  **`tool_reference` is part of the official Anthropic Messages API spec.** It is not a Claude Code internal addition.

  ### Shape

  ```json
  {
    "type": "tool_reference",
    "tool_name": "SomeToolName",
    "cache_control": { "type": "ephemeral" }  // optional
  }
  ```

  The API reference documents this as `ToolReferenceBlockParam` with the description: *"Tool reference block that can be included in tool_result content."*

  ### Purpose

  `tool_reference` blocks are the mechanism for **deferred/dynamic tool loading** via the **Tool Search** feature (introduced Nov 2025). The flow works like this:

  1. You send tool definitions with `defer_loading: true` -- these tools are NOT loaded into Claude's context upfront (saving tokens).
  2. When Claude needs a tool, it calls the tool search tool (either `tool_search_tool_regex_20251119` or `tool_search_tool_bm25_20251119`).
  3. The API returns a `tool_search_tool_result` block containing `tool_references` -- an array of `{ type: "tool_reference", tool_name: "..." }` objects pointing to discovered tools.
  4. The API automatically expands these references into full tool definitions before showing them to Claude.
  5. Claude can then call the discovered tools.

  ### Where they appear in session JSONL

  In Claude Code sessions, `tool_reference` blocks appear inside `tool_result.content` arrays. This happens in two scenarios:

  1. **Server-side tool search results**: When the built-in tool search runs, the response contains `tool_search_tool_result` blocks with nested `tool_references` arrays of `tool_reference` objects.

  2. **Client-side / custom tool search**: Claude Code implements its own `ToolSearch` tool (the one visible at the top of this conversation). When its tool search result is sent back to the API, it uses the standard `tool_result` format with `tool_reference` content blocks:
     ```json
     {
       "type": "tool_result",
       "tool_use_id": "toolu_...",
       "content": [
         { "type": "tool_reference", "tool_name": "discovered_tool_name" }
       ]
     }
     ```

  The documentation explicitly notes: *"Every tool referenced must have a corresponding tool definition in the top-level `tools` parameter with `defer_loading: true`."* If a `tool_reference` points to a tool not in the `tools` array, you get a 400 error.

  ### Content block types allowed in `tool_result.content`

  According to the Messages API reference, these types can appear in `tool_result` content arrays:
  1. `TextBlockParam` (type: "text")
  2. `ImageBlockParam` (type: "image")
  3. `SearchResultBlockParam` (type: "search_result")
  4. `DocumentBlockParam` (type: "document")
  5. `ToolReferenceBlockParam` (type: "tool_reference")

  ### Bottom line

  `tool_reference` is a **first-class official API type**, not a Claude Code hack. Claude Code uses it because it implements client-side tool search (the `ToolSearch` tool you see in its system prompt) to dynamically load deferred tools like MCP tools and plugin tools, keeping the context window efficient.
