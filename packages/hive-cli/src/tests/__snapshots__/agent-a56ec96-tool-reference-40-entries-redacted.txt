  ## Claude Code Session Format (JSONL)

  Claude Code CLI automatically saves all your conversations in JSONL format at ~/.claude/projects/. Each session is a .jsonl file — one JSON object per line, containing every message, tool call, and response.

  ### Session Structure

  Every record has a sessionId, timestamp, and uuid. The parentUuid field chains records into a linked list — each record points to the one before it.

  ### Key Fields in Records

  Example records include fields like parentUuid, isSidechain, userType, cwd (current working directory), sessionId, version, type (message type), message content with role and content, uuid, and timestamp.

  ### Session Continuation

  Continuation files begin with a compact_boundary record that also exists in the parent file. It's a byte-for-byte duplicate. The parentUuid field bridges the gap — the new session's first record has parentUuid pointing to the old session's last record. Follow the chain and you'll cross the boundary seamlessly.

  This JSONL format allows tools and scripts to parse Claude Code session histories and reconstruct full conversations across session boundaries and compactions.

  ### Agents flag format

  | Field             | Required | Description                                                                                                                                                                                                         |

  ### System prompt flags

  Claude Code provides four flags for customizing the system prompt. All four work in both interactive and non-interactive modes.

  | Flag                          | Behavior                                    | Use case                                                             |
  | :---------------------------- | :------------------------------------------ | :------------------------------------------------------------------- |
  | `--system-prompt`             | **Replaces** entire default prompt          | Complete control over Claude's behavior and instructions             |
  | `--system-prompt-file`        | **Replaces** with file contents             | Load prompts from files for reproducibility and version control      |
  | `--append-system-prompt`      | **Appends** to default prompt               | Add specific instructions while keeping default Claude Code behavior |
  | `--append-system-prompt-file` | **Appends** file contents to default prompt | Load additional instructions from files while keeping defaults       |

  **When to use each:**

  * **`--system-prompt`**: use when you need complete control over Claude's system prompt. This removes all default Claude Code instructions, giving you a blank slate.
    ```bash  theme={null}
    claude --system-prompt "You are a Python expert who only writes type-annotated code"
    ```

  * **`--system-prompt-file`**: use when you want to load a custom prompt from a file, useful for team consistency or version-controlled prompt templates.
    ```bash  theme={null}
    claude --system-prompt-file ./prompts/code-review.txt
    ```

  * **`--append-system-prompt`**: use when you want to add specific instructions while keeping Claude Code's default capabilities intact. This is the safest option for most use cases.
    ```bash  theme={null}
    claude --append-system-prompt "Always use TypeScript and include JSDoc comments"
    ```

  * **`--append-system-prompt-file`**: use when you want to append instructions from a file while keeping Claude Code's defaults. Useful for version-controlled additions.
    ```bash  theme={null}
    claude --append-system-prompt-file ./prompts/style-rules.txt
    ```

  `--system-prompt` and `--system-prompt-file` are mutually exclusive. The append flags can be used together with either replacement flag.

  For most use cases, `--append-system-prompt` or `--append-system-prompt-file` is recommended as they preserve Claude Code's built-in capabilities while adding your custom requirements. Use `--system-prompt` or `--system-prompt-file` only when you need complete control over the system prompt.

     519→   519→## Tool definition
     520→   520→
     521→   521→The tool search tool has two variants:
     522→   522→
     523→   523→```json JSON
     524→   524→{
     525→   525→  "type": "tool_search_tool_regex_20251119",
     526→   526→  "name": "tool_search_tool_regex"
     527→   527→}
     528→   528→```
     529→   529→
     530→   530→```json JSON
     531→   531→{
     532→   532→  "type": "tool_search_tool_bm25_20251119",
     533→   533→  "name": "tool_search_tool_bm25"
     534→   534→}
     535→   535→```
     536→   536→
     537→   537→<Warning>
     538→   538→**Regex variant query format: Python regex, NOT natural language**
     539→   539→
     540→   540→When using `tool_search_tool_regex_20251119`, Claude constructs regex patterns using Python's `re.search()` syntax, not natural language queries. Common patterns:
     541→   541→
     542→   542→- `"weather"` - matches tool names/descriptions containing "weather"
     543→   543→- `"get_.*_data"` - matches tools like `get_user_data`, `get_weather_data`
     544→   544→- `"database.*query|query.*database"` - OR patterns for flexibility
     545→   545→- `"(?i)slack"` - case-insensitive search
     546→   546→
     547→   547→Maximum query length: 200 characters
     548→   548→
     549→   549→</Warning>
     550→   550→
     551→   551→<Note>
     552→   552→**BM25 variant query format: Natural language**
     553→   553→
     554→   554→When using `tool_search_tool_bm25_20251119`, Claude uses natural language queries to search for tools.
     555→   555→
     556→   556→</Note>
     557→   557→
     558→   558→### Deferred tool loading
     559→   559→
     560→   560→Mark tools for on-demand loading by adding `defer_loading: true`:
     561→   561→
     562→   562→```json JSON
     563→   563→{
     564→   564→  "name": "get_weather",
     565→   565→  "description": "Get current weather for a location",
     566→   566→  "input_schema": {
     567→   567→    "type": "object",
     568→   568→    "properties": {
     569→   569→      "location": { "type": "string" },
     570→   570→      "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }
     571→   571→    },
     572→   572→    "required": ["location"]
     573→   573→  },
     574→   574→  "defer_loading": true
     575→   575→}
     576→   576→```
     577→   577→
     578→   578→**Key points:**
     579→   579→
     580→   580→- Tools without `defer_loading` are loaded into context immediately
     581→   581→- Tools with `defer_loading: true` are only loaded when Claude discovers them via search
     582→   582→- The tool search tool itself should **never** have `defer_loading: true`
     583→   583→- Keep your 3-5 most frequently used tools as non-deferred for optimal performance
     584→   584→
     585→   585→Both tool search variants (`regex` and `bm25`) search tool names, descriptions, argument names, and argument descriptions.
     586→   586→
     587→   587→## Response format
     588→   588→
     589→   589→When Claude uses the tool search tool, the response includes new block types:
     590→   590→
     591→   591→```json JSON
     592→   592→{
     593→   593→  "role": "assistant",
     594→   594→  "content": [
     595→   595→    {
     596→   596→      "type": "text",
     597→   597→      "text": "I'll search for tools to help with the weather information."
     598→   598→    },
     599→   599→    {
     600→   600→      "type": "server_tool_use",
     601→   601→      "id": "srvtoolu_01ABC123",
     602→   602→      "name": "tool_search_tool_regex",
     603→   603→      "input": {
     604→   604→        "query": "weather"
     605→   605→      }
     606→   606→    },
     607→   607→    {
     608→   608→      "type": "tool_search_tool_result",
     609→   609→      "tool_use_id": "srvtoolu_01ABC123",
     610→   610→      "content": {
     611→   611→        "type": "tool_search_tool_search_result",
     612→   612→        "tool_references": [{ "type": "tool_reference", "tool_name": "get_weather" }]
     613→   613→      }
     614→   614→    },
     615→   615→    {
     616→   616→      "type": "text",
     617→   617→      "text": "I found a weather tool. Let me get the weather for San Francisco."
     618→   618→    },
     619→   619→    {
     620→   620→      "type": "tool_use",
     621→   621→      "id": "toolu_01XYZ789",
     622→   622→      "name": "get_weather",
     623→   623→      "input": { "location": "San Francisco", "unit": "fahrenheit" }

     625→   625→  ],
     626→   626→  "stop_reason": "tool_use"
     627→   627→}
     628→   628→```
     629→   629→
     630→   630→### Understanding the response
     631→   631→
     632→   632→- **`server_tool_use`:** Indicates Claude is invoking the tool search tool
     633→   633→- **`tool_search_tool_result`:** Contains the search results with a nested `tool_search_tool_search_result` object
     634→   634→- **`tool_references`:** Array of `tool_reference` objects pointing to discovered tools
     635→   635→- **`tool_use`:** Claude invoking the discovered tool
     636→   636→
     637→   637→The `tool_reference` blocks are automatically expanded into full tool definitions before being shown to Claude. You don't need to handle this expansion yourself. It happens automatically in the API as long as you provide all matching tool definitions in the `tools` parameter.

    1013→  1013→## Custom tool search implementation
    1014→  1014→
    1015→  1015→You can implement your own tool search logic (e.g., using embeddings or semantic search) by returning `tool_reference` blocks from a custom tool. When Claude calls your custom search tool, return a standard `tool_result` with `tool_reference` blocks in the content array:
    1016→  1016→
    1017→  1017→```json JSON
    1018→  1018→{
    1019→  1019→  "type": "tool_result",
    1020→  1020→  "tool_use_id": "toolu_your_tool_id",
    1021→  1021→  "content": [{ "type": "tool_reference", "tool_name": "discovered_tool_name" }]
    1022→  1022→}
    1023→  1023→```
    1024→  1024→
    1025→  1025→Every tool referenced must have a corresponding tool definition in the top-level `tools` parameter with `defer_loading: true`. This approach lets you use more sophisticated search algorithms while maintaining compatibility with the tool search system.
    1026→  1026→
    1027→  1027→<Note>
    1028→  1028→The `tool_search_tool_result` format shown in the [Response format](#response-format) section is the server-side format used internally by Anthropic's built-in tool search. For custom client-side implementations, always use the standard `tool_result` format with `tool_reference` content blocks as shown above.
    1029→  1029→</Note>
    1030→  1030→
    1031→  1031→For a complete example using embeddings, see our [tool search with embeddings cookbook](https://platform.claude.com/cookbooks).
    1032→  1032→

    1092→  1092→### Common mistakes
    1093→  1093→
    1094→  1094→<section title="400 Error: All tools are deferred">
    1095→  1095→
    1096→  1096→**Cause:** You set `defer_loading: true` on ALL tools including the search tool
    1097→  1097→
    1098→  1098→**Fix:** Remove `defer_loading` from the tool search tool:
    1099→  1099→
    1100→  1100→```json
    1101→  1101→{
    1102→  1102→  "type": "tool_search_tool_regex_20251119", // No defer_loading here
    1103→  1103→  "name": "tool_search_tool_regex"
    1104→  1104→}
    1105→  1105→```
    1106→  1106→
    1107→  1107→</section>
    1108→  1108→
    1109→  1109→<section title="400 Error: Missing tool definition">
    1110→  1110→
    1111→  1111→**Cause:** A `tool_reference` points to a tool not in your `tools` array
    1112→  1112→
    1113→  1113→**Fix:** Ensure every tool that could be discovered has a complete definition:
    1114→  1114→
    1115→  1115→```json
    1116→  1116→{
    1117→  1117→  "name": "my_tool",
    1118→  1118→  "description": "Full description here",
    1119→  1119→  "input_schema": {
    1120→  1120→    // complete schema
    1121→  1121→  },
    1122→  1122→  "defer_loading": true
    1123→  1123→}
    1124→  1124→```
    1125→  1125→
    1126→  1126→</section>
    1127→  1127→
    1128→  1128→<section title="Claude doesn't find expected tools">
    1129→  1129→
    1130→  1130→**Cause:** Tool names or descriptions don't match the regex pattern
    1131→  1131→
    1132→  1132→**Debugging steps:**
    1133→  1133→
    1134→  1134→1. Check tool name and description. Claude searches BOTH fields
    1135→  1135→2. Test your pattern: `import re; re.search(r"your_pattern", "tool_name")`
    1136→  1136→3. Remember searches are case-sensitive by default (use `(?i)` for case-insensitive)
    1137→  1137→4. Claude uses broad patterns like `".*weather.*"` not exact matches
    1138→  1138→
    1139→  1139→**Tip:** Add common keywords to tool descriptions to improve discoverability
    1140→  1140→
    1141→  1141→</section>

  ## `tool_reference` content blocks -- full explanation

  **`tool_reference` is part of the official Anthropic Messages API spec.** It is not a Claude Code internal addition.

  ### Shape

  ```json
  {
    "type": "tool_reference",
    "tool_name": "SomeToolName",
    "cache_control": { "type": "ephemeral" }  // optional
  }
  ```

  The API reference documents this as `ToolReferenceBlockParam` with the description: *"Tool reference block that can be included in tool_result content."*

  ### Purpose

  `tool_reference` blocks are the mechanism for **deferred/dynamic tool loading** via the **Tool Search** feature (introduced Nov 2025). The flow works like this:

  1. You send tool definitions with `defer_loading: true` -- these tools are NOT loaded into Claude's context upfront (saving tokens).
  2. When Claude needs a tool, it calls the tool search tool (either `tool_search_tool_regex_20251119` or `tool_search_tool_bm25_20251119`).
  3. The API returns a `tool_search_tool_result` block containing `tool_references` -- an array of `{ type: "tool_reference", tool_name: "..." }` objects pointing to discovered tools.
  4. The API automatically expands these references into full tool definitions before showing them to Claude.
  5. Claude can then call the discovered tools.

  ### Where they appear in session JSONL

  In Claude Code sessions, `tool_reference` blocks appear inside `tool_result.content` arrays. This happens in two scenarios:

  1. **Server-side tool search results**: When the built-in tool search runs, the response contains `tool_search_tool_result` blocks with nested `tool_references` arrays of `tool_reference` objects.

  2. **Client-side / custom tool search**: Claude Code implements its own `ToolSearch` tool (the one visible at the top of this conversation). When its tool search result is sent back to the API, it uses the standard `tool_result` format with `tool_reference` content blocks:
     ```json
     {
       "type": "tool_result",
       "tool_use_id": "toolu_...",
       "content": [
         { "type": "tool_reference", "tool_name": "discovered_tool_name" }
       ]
     }
     ```

  The documentation explicitly notes: *"Every tool referenced must have a corresponding tool definition in the top-level `tools` parameter with `defer_loading: true`."* If a `tool_reference` points to a tool not in the `tools` array, you get a 400 error.

  ### Content block types allowed in `tool_result.content`

  According to the Messages API reference, these types can appear in `tool_result` content arrays:
  1. `TextBlockParam` (type: "text")
  2. `ImageBlockParam` (type: "image")
  3. `SearchResultBlockParam` (type: "search_result")
  4. `DocumentBlockParam` (type: "document")
  5. `ToolReferenceBlockParam` (type: "tool_reference")

  ### Bottom line

  `tool_reference` is a **first-class official API type**, not a Claude Code hack. Claude Code uses it because it implements client-side tool search (the `ToolSearch` tool you see in its system prompt) to dynamically load deferred tools like MCP tools and plugin tools, keeping the context window efficient.
