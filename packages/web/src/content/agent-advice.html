Agent Advice That Generalizes

Yoav Tzfati · November 19, 2026

I've spent most of this year helping AI safety researchers use coding agents, at MATS and other places. By now most of the advice I give is repeated, and this post is that part. It's a living document: I'll keep updating it as I find better ways to use agents, so consider checking back every so often.

What I try to improve is the difficulty of task people can hand to their agent while trusting that the result will be good, so they won't have to throw it away or find out weeks later that it was wrong.

For some of the problems below, part of the best solution I've found so far is a tool I built. The tools all install from one place, alignment-hive:

curl -fsSL https://alignment-hive.com/install.sh | bash

That adds my plugin marketplace and the hive plugin, and running /hive:align in Claude Code then recommends the rest. The problems come first, though: the tools are my work-in-progress answer, not the only one.

The examples throughout this post come from building one of those tools, tldr: a small plugin that collapses each long agent reply to a one-sentence summary, with [ more ] to open the full reply. Messages are verbatim unless labelled made up, and [...] marks text I left out.

Remove the friction first

Doing something your agent could have done costs you a context switch. It adds up to a lot of attention and fatigue.

So whenever I notice myself doing something on behalf of an agent, I ask whether I can connect it instead. For example:

  • Auto mode. Claude Code's terminal sessions default to it. A classifier checks each command, so you aren't approving them one by one. /auto-mode-setup helps you configure its permissions.
  • Your data sources. Email, Slack, docs, cloud storage.
  • Your compute provider, like RunPod or Vast.ai.
  • Computer use, for whatever has no connector.
  • A way to check its own work. So it can run what it built and catch errors itself.

Prompt to pasteinto your own agent

Look through my recent sessions in this project for things I did by hand that you could have done yourself with the right access: text I pasted in from Slack, email or docs, commands I ran for you, results I copied back. For each one, tell me which connector, CLI or permission would let you do it next time, and set up the ones you can.

I install Claude Code on every GPU machine I rent

A common setup, but that agent can't add GPUs or stop using the one it's sitting on, so managing compute stays your job.

What I recommend instead is one persistent machine that all your agents run on, with access to spin up and use execution environments on their own. Anthropic's managed agents post calls this decoupling the brain from the hands. My remote-kernels plugin is the hands part for RunPod, vast.ai and Kubernetes.

I wouldn't use your laptop, since your sessions stop whenever it sleeps. I'd make the persistent machine a dedicated computer that stays on, a cloud server, or your university cluster's login node. Cloud servers cost more in the long run and lack a residential IP address, but they're still a good choice, especially when your org provides one.

What about security?

I see lots of people keep friction in the name of security. If you back up your data, keep sensitive resources your agent doesn't need somewhere it can't access, and otherwise make the connections above to every piece of context that could be useful, you are very likely making the right tradeoff.

"Somewhere it can't access" is ideally a different computer from the one your agents run on, especially for your crypto.

These measures also protect you from software supply chain attacks, since your agent is going to be installing a bunch of software. That risk is likely as high as, if not higher than, the risk of the agent taking misaligned actions. As for prompt injection, various Anthropic staff have said publicly that it's essentially solved in practice once you count the mitigations built into their products.

In the loop, out of the loop

A lot of fatigue comes from checking on an agent every so often: giving it an answer, getting it unstuck. What I do about it is decide, at every moment, which of two modes I'm in with a session, and tell the agent.

In the loop, I'm looking at this one session and nothing else. That's calmer and easier to get into flow, since a lot of the impatience comes from switching quickly between sessions. When I've said what I need to, I send it off and leave the loop. I don't look at the session again until it's fully finished, or fully ready for my next in-the-loop phase.

The most common pattern is a spec phase, an execution phase and a review phase, but it isn't a rule. In-the-loop phases are for communicating intent, whenever they happen.

In the loop is a meeting

I try to say everything I care about, with the agent's help finding what I haven't thought to say, and leave the rest to it. Often I give the high-level objective and ask to be interviewed. Sometimes I do a multi-minute voice-to-text dump first, or ask for a prototype. Thariq Shihipar's field guide to finding your unknowns has more.

Speed matters here: often you want less than a minute between interactions. So I treat the phase as a synchronous meeting and tell the agent that. Effort is on low or medium. Anything slow that the conversation needs (finding information, building a prototype, running a check) goes to a subagent. Replies are short and move the discussion forward one step. There's no alignment-hive skill for this, because people like their meetings differently, so ask for what you want, and rely on memory or a small skill of your own to get it every time.

When I say "spec", lots of people assume I mean a document. I recommend against writing one, and I don't use plan mode anymore. The spec is the entire conversation up to the send-off. Any other record of it is lossy. Worse, a written spec commits the task to details the agent decided to put in, which I never saw and which don't matter, and whoever executes it can spend lots of time on those or sacrifice important details for them.

The send-off

The main way I see attention wasted at the send-off is an end point that isn't ambitious enough. The agent stops after a small step and you're needed again.

Once speccing is over, I ask the agent to keep going until the next step would be irreversible and needs my judgement, like kicking off a long experiment or pushing to main. To get that far without me, it needs what a manager who's rarely in contact would tell their team: what should get done, which decisions they can make on their own, how to handle contingencies, and how to report back. Sometimes my next in-the-loop phase isn't needed at all, because I've said the agent can land a change it's confident in without my review.

The report

Everyone is struggling with how much of their agents' work to review. Some review all of it and feel left behind. Some review none of it, and that's how slop gets into your codebase and incorrect conclusions get read off your data.

For anything nontrivial, I ask for a report at the end of the out-of-the-loop phase: an HTML page, published as a Claude Code artifact, where I can select something and send a comment to Claude. The agent iterates not only on the work but on the way it's presented to me, so that my next in-the-loop phase is as effective as possible. My debrief plugin is tooling and a skill for writing these: what was done and why, decisions with the highest risk of not being what I meant, side effects, and how the work was verified. It's in beta; asking for a report in your own words works too.

The report is how I keep understanding work I didn't do myself. If part of my goal is to learn how something works, I say so in the spec and ask for more detail in the report, and when I'm lost I tell the agent and ask for the report to explain it to me. That has worked very well for me. Still, the most common complaint I hear from researchers is that it's hard to understand what their agent did well enough to give it the right input, especially in math. So I'm planning to invest in this heavily in the near future.

Review doesn't need quick replies the way a meeting does, because there's a whole page to react to. Often I leave a bunch of comments and send the agent straight into another out-of-the-loop phase without a single in-the-loop turn.

Spending more tokens

The best way I know to get results I can trust, with fewer mistakes, is spending more tokens. Tokens are cheap relative to your time. The agent won't necessarily spend them unprompted: it's totally possible to get back a result the agent itself doesn't trust, because it didn't know it was allowed to spend more.

Review agents are the bread and butter. The thing people most often tell me afterwards really helped their work is having a GPT model review everything Claude does: the plan, then the code, then the analysis of the results. What a second model family adds is a reviewer that's less correlated with the model that did the work, though review by the same model is still really good. The labs don't offer ways for models from different labs to collaborate, so I built model-router, a plugin that makes GPT models native subagents inside Claude Code. The simple alternative is telling Claude to spawn the Codex CLI when it needs to. Cross-family work is another area I'm planning to keep investing in heavily: as third-party researchers we aren't tied to one lab's products, and I think that's one of our biggest leverage points.

Memory

An agent has to ask lots of small questions to do a task the way you want. Next time you do a similar task, it has forgotten your answers and has to ask again. That's why current models have a prior that you don't want to be asked many questions: they ask about the most important things and guess the rest. So it helps to say that asking is fine. It helps more to have memory, which also makes it less costly to spend time specifying.

I don't rely on memories the model writes for itself. They often mis-generalize: a mistake that depended on context gets remembered as a never-do, or the wrong reasoning gets written down for an instruction. Writing good memories is incredibly hard. Knowing the current task and looking into the past for relevant interactions is much easier.

My hive plugin makes the content of my past sessions easily accessible to the current session, and encourages the agent to use it. That's one of the reasons I keep all my agents on one machine.

There will be tasks that are too hard. Delegate one and you get such a volume of sloppy output that it isn't worth your time to review, and you have to go back and break it down. So I'd apply everything above to whatever you're delegating now, work up from there, and keep an eye on the quality you're getting.

A full research question is out of reach for all but the simplest questions, though I'm starting to see some examples, and the bottleneck seems to be the write-up more than the experiment. If you get close to delegating one, your research probably isn't very counterfactual: as the big labs spend more compute on alignment research, the easy-to-delegate questions will be handled autonomously. So be more ambitious, and look for work that depends on your human insight to succeed.

Questions I get

Should I be running lots of agents at once?

Yes, eventually, but I don't recommend trying too hard; let it come naturally. Once your sessions run a long time without needing you, concurrency comes almost for free. Parallelizing before then means switching between sessions that each still need you. It isn't technically hard: you may need to understand git worktrees and need an interface to start and list sessions (I use the terminal's agents view; some people use the desktop app).

Going up the ladder often substitutes for concurrency: one session running a range of experiments replaces several running one each. The limit is one orchestrator session for the whole project. Some people like that; I don't that much, since I have a good memory system and want to review tasks independently.

Can I see an example on a research task?

Not one of mine yet; I haven't done research in about a year. This advice comes from sessions with researchers and is at least partly generalized from my software work. If you have research prompts that show one of these points better, send them and I might feature them here.

Could a misaligned agent sabotage my research?

I don't have a complete solution to this. That said, I think getting used to review reports helps: understanding what your agent is doing at the right level, and not compromising on your understanding. As time goes on, I can see this kind of process integrating dumber, more trusted models that review the report and make sure it's honest about what happened: control and scalable oversight techniques, built into the work we actually do as researchers.
