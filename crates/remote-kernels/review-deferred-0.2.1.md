## [high][concurrency] sync() holds the per-machine operation lock across the entire upload, starving the lease heartbeat until the machine-side watchdog self-finalizes mid-sync
/Users/yoav/projects/alignment-hive/.claude/worktrees/remote-kernels-lifecycle/crates/remote-kernels/src/server.rs:2641

sync() acquires `_mutation_guard` (the machine oplock, server.rs:2636) and keeps it held across `conn.upload(...).await` (server.rs:2641), which for a large project or slow uplink runs unboundedly long. The heartbeat loop must re-acquire that same flock every 60s tick before it can refresh the lease (heartbeat.rs:275-292), so during the upload no `refresh` (and no legacy `conn.heartbeat()`) runs. The on-machine watchdog treats the lease ts / heartbeat file as liveness and arms `disconnect` once `now - last_valid_touch >= stale_secs` (default 300s; rk-watchdog.sh:361-374). With kernels idle (typical while syncing data), finish_armed proceeds immediately to run_finalize and `exec $action_cmd` (rk-watchdog.sh:224-247, 299-326), stopping or terminating the machine per its cleanup policy. Concrete failure: attached supervised machine + `sync()` of a dataset taking >~6 minutes -> machine stops/terminates itself mid-upload, sync fails, the server discovers the Finalizing fence on its next refresh, and on cleanup=terminate all machine data is gone. Contrast: explicit_cleanup_instance deliberately releases the oplock during long pre-stop commands 'so the heartbeat can keep the lease fresh'

## [medium][lifecycle] lifecycle.json read-modify-writes race across two different locks — a freshly queued finish plan can be silently erased (or a cleared one resurrected)
/Users/yoav/projects/alignment-hive/.claude/worktrees/remote-kernels-lifecycle/crates/remote-kernels/src/server.rs:5071

finish() and finish_drain serialize their lifecycle.json read-modify-writes with the in-process state lock (lines 1197-1208, 1398-1406, 1459-1470; comment at 1189 claims intent writes "race only against other in-process writers (the drain)"), but explicit_cleanup_instance writes lifecycle.json holding only the machine oplock (load at 5071, saves at 5086, 5104, 5108, 5127), and shutdown_cleanup does the same (5366-5384). Concrete lost update: stop() (from user or the drain path of a different plan) loads lifecycle at 5071 without the intent, a concurrent finish() writes its intent and returns "Finish plan queued", then stop()'s save at 5086/5127 writes the pre-intent snapshot back — the acknowledged plan vanishes, downloads never happen, and status() never mentions it. The inverse interleaving (stop() loads while intent present, drain clears it at 1459-1470, stop() saves it back) resurrects an already-executed plan, so a later attach() (line 874-879) re-runs it and stops/terminates the machine unexpectedly right after reconnecting. All lifecycle.json writers need one consistent lock (the oplock or the state lock, not either-or).

## [medium][scripts] Watchdog exits permanently on observing server-driven finalizing; revert-to-armed after provider rejection leaves the machine unsupervised
crates/remote-kernels/scripts/machine/rk-watchdog.sh:383

supervise treats finalizing as terminal and exits (rk-watchdog.sh:382-384, 2s poll). In explicit_cleanup_instance the server enters finalizing, calls the provider, and on an authoritative rejection with the machine still Running calls revert_to_armed and bails (src/server.rs:5059-5104) — restoring the lease to active, but the watchdog has almost certainly observed the multi-second finalizing window and exited, and install_watchdog is only ever invoked at heartbeat-pipeline start (heartbeat.rs:262), never after a revert. The session then continues with lease refreshes succeeding but no machine-side supervisor: if the server later dies, nothing ever arms disconnect and the machine bills unbounded (the boot-scoped orphan guard fired once long ago). ## [low][scripts] vast Jupyter launch embeds the token in single quotes without the crate's own shell-safety validation
crates/remote-kernels/src/runtime/vast.rs:893

open() validates workdir, ssh-user, and jupyter-command as shell-safe, but then interpolates ctx.jupyter_token raw into `export REMOTE_KERNELS_JUPYTER_TOKEN='{}'` (vast.rs:892-900). Freshly generated tokens are hex (server.rs:320-325), but tokens are also loaded back from persisted instance records (server.rs:417-418, 781): a record whose jupyter_token field contains a single quote (hand-edited, corrupted, or written by a future/foreign tool version) becomes shell code executed on the machine, and at minimum breaks the launch confusingly. ## [low][scripts] The no-single-quotes invariant that lease transport relies on is enforced only by a comment

invoke() interpolates the entire rk-lease.sh source raw inside a single-quoted `bash -c '{LEASE}'` (machine_scripts.rs:279-281), relying on the script containing zero single quotes (currently true for both scripts — verified).
